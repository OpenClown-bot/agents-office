## Communication style with the PO

The PO is Russian-speaking, comfortable with terminal/git/Markdown, and **explicitly learning AI engineering through this project**. Treat every interaction as both efficient orchestration AND a teaching opportunity.

**Patterns that work well**:
- Tables for trade-offs (Pro/Con; Option A/B/C with cost/benefit)
- Concrete commands, not vague suggestions
- 2-4 named options when asking for decisions
- Honest "I don't know" rather than confident guesses
- Short paragraphs — no walls of text
- Direct disagreement when PO is wrong, with reasoning
- Use `<ref_file file="..." />` and `<ref_snippet file="..." lines="..." />` citations when referring to specific code/docs
- Send screenshots as attachments via `message_user`, not as base64 in markdown

**Anti-patterns to avoid**:
- Validation-seeking phrases ("отличный вопрос!", "хорошая идея!")
- Vague closures ("давай попробуем", "может сработать")
- Hidden mistakes — surface them immediately, root-cause them, fix them
- Apologetic preambles
- Never claim success without verifiable evidence (test output, CI status, validate_docs result)

## Pitfalls / lessons from this session

1. **Reviewer NEVER promotes `status: approved`.** PO approval = PR merge. The Reviewer artifact stays at `status: in_review` for its lifetime. The orchestrator's re-review prompt template MUST NOT include status-bump instructions.

2. **Pinpoint Reviewer at 20-minute mark.** If Kimi K2.6 hasn't pushed a commit to her branch by then, send a directive nudge to start writing the review file. She tends to over-deliberate.

3. **`validate_docs.py` regex falsely flags sub-ticket IDs.** When working with TKT-XXXa/b/c, escape the hyphen in headings: `TKT&#45;003a:` instead of `TKT-003:`. Existing examples: `TKT-005a-approval-queue-core.md:16` etc.

4. **Required frontmatter fields for tickets** (per `validate_docs.py:55`): `id, title, status, arch_ref, assigned_executor, created`. Even draft tickets need `assigned_executor` filled (use planned executor model).

5. **CI failures often indicate process gaps, not bugs.** PR#11's validate-docs failure was caused by Executor adding `TKT-001 outputs` (unpinned) in §10 Execution Log. Reviewer caught it during her review without prompting. The validator is tight on purpose.

6. **Merge order matters**: code PR first, review PR second. Always.

7. **Tokens stay safe.** Never commit secrets to repo. The `GITHUB_TOKEN_OPENCLOWN` is in user-scope secrets, automatically available in shell as env var. Do NOT print or echo it.
